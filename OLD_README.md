Ниже представлен подробный технический проект (Technical Specification) для утилиты mongo-schema-fetch.
## 1. Технологический стек и проверенные пакеты
Чтобы минимизировать написание собственного сложного кода (особенно для парсинга BSON-типов), мы будем использовать официальные и проверенные временем инструменты:
 * **Язык:** TypeScript (Node.js). Обеспечивает строгую типизацию входных аргументов и выходного JSON-контракта.
 * **Парсинг CLI:** commander (стандарт де-факто для Node.js CLI) или yargs.
 * **Драйвер БД:** mongodb (официальный Node.js драйвер).
 * **Анализ схемы (Киллер-фича):** mongodb-schema. Это официальный, но малоизвестный пакет от самой MongoDB. Он принимает массив документов и автоматически вычисляет вероятностную схему, определяя типы и даже пересечения типов (например, если поле в 90% случаев String, а в 10% Number). Это избавит нас от написания собственного парсера BSON.
 * **Тестирование:** vitest (или jest) для Unit-тестов и testcontainers (пакет @testcontainers/node) для запуска реальных баз в Docker во время Acceptance-тестов.
## 2. Что еще собирать? (Расширенная модель данных)
Помимо базовых 4 блоков, для точной симуляции базы (Environment Simulation) нам понадобятся дополнительные метрики.
**Блок 1: Server & Host Context (Как получить: db.adminCommand({ buildInfo: 1 }), hostInfo)**
 * Версия MongoDB и архитектура (x86_64/ARM).
 * Количество доступной оперативной памяти и ядер CPU на сервере клиента (критично для понимания того, как планировщик БД распределяет память под сортировки internalQueryExecMaxBlockingSortBytes).
 * Параметры механизма хранения (WiredTiger cache size).
**Блок 2: Collection Stats (Как получить: db.collection.stats())**
 * Точное и оценочное количество документов (count и estimatedDocumentCount).
 * Средний размер документа (avgObjSize).
 * Общий размер индексов коллекции (totalIndexSize).
**Блок 3: Индексы и их использование (Как получить: db.collection.getIndexes(), $indexStats)**
 * Сам массив существующих индексов (ключи, направления, флаги вроде unique или sparse).
 * **Статистика использования (New):** Агрегация $indexStats покажет, сколько раз каждый индекс реально использовался. Если индекс не использовался ни разу, наша LLM в отчете может сразу предложить его удалить для экономии RAM.
**Блок 4: Анализ схемы и Кардинальность (Как получить: агрегация $sample + mongodb-schema)**
 * Выборка: извлечение 1000 случайных документов через $sample.
 * Структура: прогон выборки через библиотеку mongodb-schema для получения JSON-описания типов всех полей и вложенных объектов.
 * **Кардинальность (New):** Для полей с типом String и Number, если количество уникальных значений в выборке меньше 20 (например, статусы "active", "deleted"), сохраняем этот массив значений как Enum. Это критически важно для ИИ, чтобы предлагать правильный порядок ключей в составных индексах (Compound Indexes).
## 3. Use Cases (Сценарии использования)
**UC-1: Ручной профилинг разработчиком**
Разработчик расследует медленный запрос локально или на staging. Он запускает команду npx mongo-schema-fetch <uri>, получает файл schema-payload.json, визуально проверяет его на отсутствие реальных данных пользователей и загружает в ваш Web UI для получения рекомендаций.
**UC-2: Интеграция в CI/CD (Предотвращение деградации)**
В pipeline (GitHub Actions) настроен шаг: при деплое новой версии приложения запускается mongo-schema-fetch против тестовой базы. Слепок отправляется в ваш сервис по API для проверки новых запросов. Если ИИ видит, что новые запросы требуют Full Collection Scan (нет индекса), CI-пайплайн падает с ошибкой, не пуская код в продакшен.
**UC-3: Безопасный экспорт аналитиком данных**
Аналитик или DBA запускает утилиту против вторичного узла (Secondary Replica) в production-кластере с флагом --read-preference secondary. Это позволяет собрать статистику боевой базы, вообще не нагружая основной пишущий узел (Primary).
## 4. Acceptance Criteria (Критерии приемки)
 * **AC-1 (Zero Data Leak):** В итоговом JSON-файле не должно быть никаких значений из исходной базы данных, кроме ключей коллекций, названий полей, версий БД и значений перечислений (Enum), если их кардинальность ниже заданного порога (например, < 20 уникальных значений).
 * **AC-2 (Performance):** Утилита не должна блокировать работу базы данных. Время выполнения на базе с 50 коллекциями и миллионами записей не должно превышать 60 секунд. Запросы к большим коллекциям должны быть ограничены через $sample.
 * **AC-3 (Resilience):** Утилита должна корректно обрабатывать ошибки (например, Authentication failed или Timeout) и выводить понятные человекочитаемые сообщения в консоль, а не "падать" с длинным stack trace.
 * **AC-4 (Output Contract):** Утилита должна валидировать собранный JSON против встроенной JSON Schema (например, через библиотеку ajv) перед сохранением на диск, чтобы гарантировать, что Web UI 100% сможет его прочитать.
## 5. Стратегия тестирования
**Unit-тесты (Быстрые проверки логики)**
 * Мокирование драйвера MongoDB для проверки того, как утилита парсит аргументы командной строки (URI, флаги --out, --include-collections).
 * Проверка функции маппинга: передаем сырой JSON-ответ от пакета mongodb-schema и проверяем, что наша функция очистки корректно удаляет лишнее и формирует нужный нам финальный контракт.
**Acceptance-тесты (Testcontainers)**
Это ядро стабильности. Тесты должны запускаться в Docker-окружении:
 1. **Setup:** Testcontainers поднимает контейнер mongo:6.0 и mongo:7.0 (для проверки совместимости версий).
 2. **Seed:** Тест подключается к контейнеру и заливает 10 000 синтетических документов разной структуры, создает пару индексов.
 3. **Execute:** Тест вызывает скомпилированный CLI скрипт node bin/cli.js mongodb://<динамический_порт_контейнера>.
 4. **Assert:** Тест читает сгенерированный schema-payload.json с диска и проверяет:
   * Присутствуют ли созданные коллекции?
   * Правильно ли определились типы (String, ObjectId, Date)?
   * Определились ли созданные индексы?
 5. **Teardown:** Testcontainers убивает базу.

Если у клиента в базе 500 коллекций, процесс снятия слепка (особенно $sample) может занять время и создать нагрузку. Как утилита должна вести себя по умолчанию в MVP?

Для MVP я настоятельно рекомендую использовать **Гибридный подход (Умный порог + Интерактивное меню)**. Это комбинация вариантов Б и В, которая дает идеальный баланс между безопасностью базы и первоклассным Developer Experience (DX).
Вот почему нельзя сканировать всё по умолчанию (Вариант А): главная ценность вашего продукта — безопасность и отсутствие нагрузки на продакшен. Если утилита «завесит» кластер, пытаясь сделать $sample по 500 коллекциям, пользователь больше никогда не вернется к вашему сервису. Более того, проблемный запрос (который пользователь хочет оптимизировать) обычно затрагивает 1–3 коллекции (даже с учетом $lookup), поэтому сканировать остальные 497 бессмысленно.
Вот как должна вести себя утилита в MVP:
### Идеальный Workflow для CLI (Гибридный подход)
**1. Мгновенная разведка (Дешевая операция)**
Как только утилита подключается к базе, она делает db.listCollections(). Это занимает миллисекунды и вообще не нагружает базу. Утилита узнает, сколько всего коллекций.
**2. Умный порог (Smart Threshold)**
 * **Если коллекций мало (например, ≤ 10):** Утилита автоматически сканирует их все и выдает результат. Это дает тот самый "Wow-эффект" и работу в один клик.
 * **Если коллекций много (> 10):** Утилита останавливается и выводит интерактивное меню в терминале, прося пользователя выбрать нужные.
**3. Интерактивное меню (Используйте пакет prompts или inquirer)**
Терминал должен выглядеть так:
```text
⚠️ Обнаружено 500 коллекций. Сканирование всех может занять время.
? Выберите коллекции, участвующие в вашем медленном запросе:
  Instructions: Press <space> to select, <a> to toggle all, <i> to invert selection

  ◯ users
  ◉ orders
  ◉ products
  ◯ logs_2025
  ◯ sessions

```
*Пользователь выбирает orders и products, нажимает Enter, и утилита сканирует только их.*
**4. Поддержка CI/CD и опытных пользователей (Флаг --collections)**
Если утилиту запускает скрипт (например, в GitHub Actions) или опытный DBA, который не хочет кликать меню, он должен иметь возможность передать коллекции аргументом:
npx mongo-schema-fetch <uri> --collections orders,products
В этом случае утилита пропускает интерактивное меню и сразу делает свою работу.
### Почему это лучшая стратегия для MVP?
 * **Защита от дурака:** Вы физически не даете утилите положить огромную базу случайным запуском.
 * **Экономия ваших серверных ресурсов:** Меньше мусорных коллекций в JSON = меньше токенов тратится на LLM при анализе, и быстрее поднимается синтетическая база на вашем сервере.
 * **Современный DX:** Разработчики обожают красивые CLI-интерфейсы с галочками. Это сразу повышает уровень доверия к инструменту.


Раз мы сузили круг до конкретных коллекций, как мы поступим с размером самой выборки для определения схемы? Зашьем ли мы жесткий лимит (например, всегда брать 1000 документов через $sample), или сделаем этот параметр динамическим в зависимости от размера коллекции?

Для MVP и даже для зрелых production-решений лучше всего использовать **жесткий лимит по умолчанию с возможностью переопределения (Hard Cap + Override)**.
Делать размер выборки строго динамическим (например, брать 1% от коллекции) — крайне опасная стратегия для базы данных. Если у клиента в коллекции 100 миллионов документов, 1% — это миллион записей. Извлечение и парсинг такого объема в Node.js съест всю память (OOM), а база данных получит неоправданный спайк нагрузки на сеть и CPU.
Вот как стоит реализовать этот механизм:
### Оптимальная стратегия (Как в MongoDB Compass)
К слову, официальный инструмент MongoDB Compass для вкладки "Schema" по умолчанию анализирует ровно **1000 документов**. Мы возьмем эту проверенную временем практику за основу.
**1. Лимит по умолчанию — 1000 документов**
Для 99% баз данных 1000 случайных документов более чем достаточно, чтобы определить типы всех полей (включая редкие опциональные поля) и вычислить кардинальность перечислений (Enum). В математической статистике действует закон убывающей доходности: анализ 10 000 документов даст вам ту же схему, что и 1000, но займет в 10 раз больше времени.
**2. Динамическое понижение для маленьких коллекций**
Перед запуском $sample, утилита проверяет estimatedDocumentCount().
 * Если в коллекции 500 документов, утилита просто забирает их все без aggregate([ { $sample: { size: 1000 } } ]), так как нативный find() работает быстрее, чем пайплайн агрегации с сэмплингом.
**3. Ручное управление для сложных случаев (Флаг --sample)**
В NoSQL базах существует проблема «Полиморфных схем» (когда старые документы имеют одну структуру, а новые — другую). Если клиент знает, что у него очень "грязные" данные и 1000 документов может не хватить для покрытия всех вариантов полей, он должен иметь право повысить лимит:
npx mongo-schema-fetch <uri> --sample 5000
### Технический нюанс работы $sample (Важно для разработки)
Вам нужно быть аккуратными с оператором $sample. В MongoDB он работает по-разному в зависимости от ситуации:
 * Если коллекция большая и размер сэмпла меньше 5% от коллекции, MongoDB использует псевдослучайный курсор (работает мгновенно).
 * Если условия не соблюдаются, база может попытаться сделать *in-memory sort* с добавлением случайного веса каждому документу. Это **сильно грузит RAM сервера**.
**Как себя обезопасить:**
В коде утилиты, при формировании запроса, всегда используйте проекцию ($project), чтобы не тянуть огромные вложенные массивы или бинарные данные, если они не нужны для вашей симуляции. Если ваша LLM не оптимизирует поиск по тексту внутри 10-мегабайтных полей с логами, лучше обрезать их размер на этапе сэмплинга.

Учитывая, что в MongoDB один документ может весить до 16 МБ (BSON limit), стоит ли нам добавить в утилиту механизм усечения слишком больших полей (например, длинных строк или массивов) прямо во время выборки, чтобы снизить потребление памяти нашей Node.js утилитой?

**Да, это критически важное архитектурное решение.** Если вы проигнорируете этот момент, ваша утилита гарантированно будет «падать» у крупных Enterprise-клиентов.
Давайте посчитаем: если у клиента тяжелые документы (например, с вложенными массивами логов или Base64-картинками), и средний вес документа хотя бы 5 МБ, то выборка из 1000 документов — это 5 ГБ данных.
Стандартный процесс Node.js (v8) по умолчанию падает с ошибкой JavaScript heap out of memory при достижении ~1.5–2 ГБ RAM. Плюс, скачивание 5 ГБ по сети для сбора метаданных — это непозволительно долго.
Однако возникает техническая проблема: **вы не можете обрезать поля через $project внутри базы, потому что на этом этапе вы еще не знаете схему (имена полей).**
Вот как нужно спроектировать этот механизм защиты:
### 1. Умная корректировка $sample на основе avgObjSize
Поскольку на предыдущем шаге (когда вы собираете метаданные) вы уже делаете db.collection.stats(), у вас есть параметр avgObjSize (средний размер документа в байтах). Используйте его как предохранитель!
 * **Если avgObjSize < 10 КБ:** Оставляем выборку в 1000 документов.
 * **Если avgObjSize от 10 КБ до 100 КБ:** Снижаем $sample до 300 документов.
 * **Если avgObjSize > 100 КБ:** Берем всего 50 документов.
*Почему это безопасно для схемы?* Огромные документы (по 100 КБ+) обычно раздуты за счет гигантских массивов однотипных данных или длинных текстов. Для определения того, что это массив объектов или строка, библиотеке mongodb-schema достаточно одного документа, а не тысячи.
### 2. Потоковая обработка (Streams) вместо toArray()
Самая частая ошибка при работе с MongoDB драйвером — вызов cursor.toArray(). Этот метод берет весь ответ из базы и помещает его в оперативную память Node.js в виде гигантского массива.
Вместо этого используйте **Node.js Streams**. Пакет mongodb-schema изначально создавался с поддержкой потоков.
Вам нужно направить поток (cursor) напрямую в парсер, чтобы Node.js обрабатывал и забывал документы по одному, не накапливая их в памяти:
```javascript
const mongodbSchema = require('mongodb-schema');

// Вместо cursor.toArray() делаем стриминг:
const stream = collection.aggregate([{ $sample: { size: limit } }]).stream();

mongodbSchema(stream, { semanticTypes: true }, (err, schema) => {
  if (err) throw err;
  console.log("Схема успешно сгенерирована без переполнения памяти!");
});

```
### 3. Защитный лимит курсора (maxTimeMS)
Помимо памяти, огромные документы могут загрузить CPU сервера базы данных во время выполнения $sample.
Всегда добавляйте .maxTimeMS(5000) ко всем запросам агрегации в вашей утилите. Если база не может собрать выборку за 5 секунд (например, кластер сильно перегружен), утилита должна прервать операцию, вывести предупреждение в консоль и предложить пользователю сузить поиск.
### 4. Очистка схемы перед отправкой (Post-processing)
Библиотека mongodb-schema вернет вам структуру, но иногда она может сохранять слишком длинные примеры строк (для вычисления кардинальности).
На этапе формирования финального schema-payload.json пройдитесь по полученному объекту рекурсивно и:
 * Если тип поля String и оно попало в массив уникальных значений (Enum), но длина строки > 100 символов — удалите это значение из списка. Для ИИ нет смысла знать содержание 100-символьного текста для построения индексов.
Используя стриминг и динамический размер выборки на основе avgObjSize, вы сделаете утилиту mongo-schema-fetch невероятно стабильной, независимо от того, какие монструозные документы хранит клиент.


Она должна делать **и то, и другое**. В мире качественных консольных интерфейсов (CLI) это называется подходом *«Graceful Degradation»* (постепенное упрощение).
Если вы делаете инструмент только с интерактивными меню, его невозможно будет встроить в автоматические пайплайны (CI/CD). Если делаете только флаги — обычные разработчики замучаются читать документацию (--help), чтобы понять, как запустить скрипт.
Вот как это должно быть реализовано технически:
### Режим 1: Интерактивный (Для людей)
Срабатывает по умолчанию, если пользователь просто ввел:
npx mongo-schema-fetch "mongodb://localhost:27017/my_db"
 1. **База данных:** Утилита берет базу my_db из самого URI.
 2. **Коллекции:** Утилита делает db.listCollections().
   * Выводит в терминал красивое меню (с помощью пакетов prompts или inquirer), где разработчик пробелом отмечает нужные коллекции.
   * *Пример:* «Выберите коллекции для анализа (используйте пробел): [x] users, [ ] logs, [x] orders».
### Режим 2: Тихий / Автоматический (Для скриптов и опытных DBA)
Срабатывает, если пользователь явно передал флаги. В этом случае утилита **отключает все ручные вопросы** и сразу делает работу.
```bash
npx mongo-schema-fetch "mongodb://localhost:27017" --db analytics --collections users,orders

```
**Какие флаги нужно реализовать:**
 * --db <название>: Переопределяет базу данных, если она не указана в URI или если нужно просканировать другую.
 * --collections <список>: Разделенный запятыми список коллекций (например, users,orders,products).
 * --all или --all-collections: Принудительно просканировать все коллекции в базе (полезно, если их 50 и не хочется кликать пробелом в меню).
 * --out <путь>: Куда сохранить файл (по умолчанию сохраняет schema-payload.json в текущую папку, но в CI/CD часто нужно сохранить в /tmp/schema.json).
### Важный нюанс с базами данных (Security)
Может возникнуть соблазн сделать интерактивное меню и для выбора базы данных (сделать db.adminCommand({ listDatabases: 1 }) и показать список всех баз на сервере).
**Не делайте этого по умолчанию.**
Для выполнения команды listDatabases пользователю нужны права уровня кластера (clusterMonitor или listDatabases). Если клиент создал для вашей утилиты безопасного Read-Only пользователя с доступом только к одной конкретной базе, попытка получить список всех баз приведет к ошибке Authentication/Authorization failed, и утилита упадет.
Поэтому логика работы с базой должна быть строгой: работаем только с той базой, которая указана в URI (или во флаге --db), и не пытаемся сканировать соседние базы без явного запроса.


Это тот самый момент в UX (пользовательском опыте), где продукт либо вызывает «Wow-эффект», либо теряет пользователя из-за лишнего трения.
Если заставлять человека каждый раз искать скачанный файл в папках и перетаскивать его в браузер руками, это быстро надоест. Но если отправлять данные на сервер без спроса — это убьет все доверие к безопасности.
Поэтому я рекомендую реализовать **механику "Magic Link" (Скрытый POST + Автооткрытие браузера)**. Это стандарт для современных крутых CLI-инструментов (как Vercel, Expo или Stripe CLI).
Вот как это должно работать в идеале:
### Идеальный флоу (Magic Link)
**Шаг 1: Локальное сохранение (Обязательно)**
Утилита *всегда* сначала сохраняет schema-payload.json локально на диск. Это доказывает вашу прозрачность.
**Шаг 2: Интерактивный запрос на отправку**
Сразу после сохранения файла в консоли появляется вопрос (через пакет prompts или enquirer):
```text
✅ Файл schema-payload.json успешно сохранен (12 КБ).

? Отправить эту схему в Web Optimizer и открыть браузер для анализа? (Y/n)
  (Данные будут загружены во временную защищенную сессию)

```
**Шаг 3: Магия под капотом (Если пользователь выбрал "Y")**
 1. **POST-запрос:** Утилита берет сформированный JSON и отправляет его POST-запросом на ваш открытый API (например, https://api.ваша-платформа.com/v1/sessions/cli-upload).
 2. **Ответ сервера:** Ваш бэкенд сохраняет этот слепок в кэш (например, в Redis с TTL на 1 час) и возвращает уникальный одноразовый URL: {"url": "https://ваша-платформа.com/t/xyz-12345"}.
 3. **Открытие браузера:** Утилита использует стандартный npm-пакет open (или встроенные механизмы Node.js), чтобы автоматически запустить браузер на компьютере разработчика прямо по этой ссылке.
**Шаг 4: Web UI**
Пользователь видит, как у него сам открывается браузер. На экране сразу отображается его загруженная схема базы, и курсор уже мигает в поле "Вставьте ваш проблемный MQL-запрос". Ему даже **не нужно было регистрироваться** для этого первого опыта!
### Почему эта стратегия выигрывает?
 * **Нулевое трение:** Разработчику не нужно переключаться между окнами, искать файлы в Finder/Explorer и логиниться.
 * **Полный контроль:** Если служба безопасности запрещает ему отправлять данные автоматом, он просто нажимает n (No). Файл остается у него, он может показать его безопасникам, а потом вручную загрузить на сайт.
 * **Лидогенерация:** Когда он перейдет по ссылке и увидит крутой результат оптимизации, вы можете предложить ему: *"Понравился результат? Зарегистрируйтесь (Google/GitHub), чтобы сохранить этот отчет навсегда"*. Это мощнейшая воронка конверсии.
### Что нужно для режима без интерфейса (CI/CD)
Если утилиту запускают с флагом --quiet или --out, вопрос Y/n задаваться не должен. Скрипт просто сохраняет файл и молча завершает работу.


Вводить медленный запрос нужно **исключительно на сайте (в Web UI)**.
Попытка заставить пользователя вставлять запрос в терминал — это то, что гарантированно разрушит пользовательский опыт (UX) и заставит многих бросить инструмент на полпути.
Вот почему этот шаг нужно оставить для браузера:
### 1. Боль при вставке JSON в терминал
Запросы в MongoDB (особенно Aggregation Pipelines) — это многострочные объекты со сложной вложенностью и обилием кавычек.
Например:
```javascript
db.orders.aggregate([
  { $match: { "status": "completed", "date": { $gt: ISODate("2026-01-01") } } },
  { $lookup: { from: "users", localField: "user_id", foreignField: "_id", as: "user" } }
])

```
Если пользователь попытается вставить это прямо в prompts в терминале, консоль почти наверняка «съест» переносы строк, сломает экранирование кавычек или вообще выполнит часть текста как команду. Разработчик получит ошибку парсинга и закроет вашу утилиту.
### 2. Магия полноценного редактора (Monaco Editor)
Когда браузер открывается по Magic Link, пользователь должен увидеть профессиональную рабочую среду.
Вы можете встроить на сайт редактор (например, Monaco Editor — тот же движок, что и в VS Code). В нем будет:
 * Подсветка синтаксиса MQL.
 * Поддержка многострочности и автоформатирования.
 * Валидация JSON/JS «на лету» (пользователь сразу увидит, если забыл закрыть скобку).
 * Автодополнение имен полей (ведь ваш сайт уже получил схему базы на предыдущем шаге!).
### 3. Эффект "Песочницы" (Playground)
Часто разработчик хочет оптимизировать не один конкретный запрос, а поэкспериментировать. В веб-интерфейсе он может вставить один запрос, нажать "Analyze", посмотреть результат, чуть-чуть изменить условие $match прямо в редакторе и запустить анализ снова. Если бы запрос передавался из терминала, ему пришлось бы каждый раз заново запускать CLI-команду.
### Исключение: Режим CI/CD (Для автоматизации)
Единственный случай, когда запрос должен передаваться через CLI — это полностью автоматизированные пайплайны, где нет человека.
Для этого в будущем вы можете добавить специальный флаг, принимающий путь к файлу с запросом:
```bash
npx mongo-schema-fetch --query-file ./slow-query.json --auto-analyze

```
Но для ручного сценария (MVP) флоу должен быть таким: **Терминал нужен только для безопасной выгрузки схемы -> Сайт нужен для комфортной работы с кодом и графиками.**
Мы продумали, как схема попадает на сайт и где вводится запрос. Переходя к следующему этапу: как вы планируете визуализировать результаты анализа для пользователя на сайте — будем выводить сухие цифры метрик «До/После» (например, миллисекунды и docsExamined) или хотите построить визуальное дерево плана выполнения (Explain Plan Tree), чтобы показать, где именно база буксовала?
